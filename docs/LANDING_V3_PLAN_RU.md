## 0. Что именно делают референсы (разбор по компонентам)

Ferrari и Apple рендерят страницы на клиенте, поэтому разобраны по встроенным данным
(`__NEXT_DATA__`, разметка секций), а не по тексту.

### Ferrari F80 — словарь компонентов страницы (в порядке появления)

| Компонент | Что это | Аналог для Flapp |
|---|---|---|
| `Cover` | полноэкранное видео/кадр, 1 заголовок, 1 строка | hero |
| `CarHighlights` | 4 «ключевые цифры» крупным кеглем: 1200 cv · 1050 kg downforce · 0–100 2.15 s · 799 units | полоса ключевых цифр |
| `ChapterIntro` ×3 + главы Exterior / Aerodynamics / Powertrain / Dynamic control / Interior | каждая глава = cover + детали | главы Отчёт / Велосипед / Бег / Исследования |
| `TextMaskBlock` ×6 | текст «проявляется» маской по мере скролла | подписи к пинованному визуалу |
| `MediaReveal` ×6 | медиа раскрывается при входе в вьюпорт | фреймы отчёта |
| `ScrollReel` | покадровая последовательность, прокручиваемая скроллом | скелет, который сам рисуется на кадре |
| `Hotspots` ×2 | точки на изображении, открывающие детали | углы на кадре (уже есть пины в главе «Coach») |
| `HorizontalSlider` ×5 | горизонтальная галерея, свайп на телефоне | кинограмма, 4 шага «как работает» |
| `TechSpecs` / `TechnicalDetails` | аккордеон характеристик в конце | FAQ + pricing |

Каждый highlight — заголовок + одна строка: *«Active aero taken to the extreme / Perfect
aerodynamic balance. Always.»* Ни одного абзаца на экране.

### Ferrari Luce — грамматика главы

`intro.hero → intro.video → story.videos (VideoStack) → engineering.cover → exterior.configurator
(LightConfigurator) + галереи → aerodynamics.cover + focus-on ×6 + details + tail → dynamics.cover
+ focus-on + sound + connectivity → tech.focuson (сетка) → interior.video / steering / controls /
gallery → TechSpecs ×7 → updates.cta`.

Паттерн каждой главы: **cover** (один большой визуал, заголовок, одна строка) → **focus-on**
(несколько деталей-точек на том же визуале) → **tail** (одна фраза-вывод). Есть интерактивный
«конфигуратор» — у нас на эту роль просятся живые инструменты (aero-минуты, высота седла).

### Apple MacBook Pro / iPhone 18 Pro

- Якорная полоса глав под шапкой (`ac-localnav`): Highlights · Design · Cameras · Performance …
  и справа кнопка «Buy». У нас: главы + «Analyze free».
- Hero и highlights — пары start/end кадров (213/302 на странице): видео, прокручиваемое
  скроллом; 19 `scroll-group`, 16 `sticky` — визуал пинуется, текст едет поверх.
- Плитка статистики всегда одной формы: `caption / VALUE / caption + сноска`
  («Up to / **24 hours** / battery life¹»). Цифра — заголовок, источник — сноска, не предложение.
- Плитки сравнения (2000 vs 1600 nits), селектор «с какой модели апгрейд» → у нас «ты vs
  про Коны / vs возрастная группа».
- Степпер состояний с картинкой на каждое (4 диафрагмы ƒ/1.48…ƒ/4.0) → у нас степпер
  высоты седла с углом колена на каждое положение.
- Плотность: ~1 изображение на 25–30 слов, маркетинговый текст ≈150 слов на секцию, при
  этом сами секции почти бестекстовые — объём набирается сносками и блоками покупки.
- Тёмная тема на всех «product stories», светлая — на покупке/сравнении/футере.

### Общая грамматика, которую берём

1. Экран = один визуал + одна цифра + одна строка. Текста ≤ 25 слов на экран.
2. Визуал пинуется, текст и состояния сменяются скроллом; на телефоне — свайп по горизонтали
   там, где на десктопе табы.
3. Цифры — заголовки, источники — сноски внизу страницы (наше правило «у каждого утверждения
   источник» сохраняется, меняется только форма).
4. Главы с якорной навигацией и постоянной CTA.

## 1. Трезвая оценка: что мешает это повторить и что менять нельзя

**Медиа — главный риск, но не «нет исходников».** (Исправлено 2026-11-06: первая версия плана
ошибочно утверждала, что чистых клипов нет.) В `upload/` лежат сырые клипы iPhone 15 Pro,
2816×1584, 60 fps, без оверлея: бег IMG_3979/4004/4258/4262, TT IMG_4088/4090/4148/4149. Они
снимались в зале и выглядят как зал. Покадровый тест затемнения фона с линиями скелета уже
даёт вид «продукт на чёрном» (раздел 4). Нет только красивой съёмки на улице. Полный разбор
материалов и список генераций — в разделе 4.

**Наше преимущество:** сам оверлей — это и есть «exploded view». Скелет, который рисуется на
кадре по мере скролла, — продуктовый визуал, а не декорация, и он у нас есть в данных
(`timeline.py` отдаёт ряды углов по кадрам; landmarks можно экспортировать для одного
клипа — это килобайты SVG, не сотни WebP-кадров как у Apple).

**Сентябрьское решение «лендинг в покое»** (`tests/test_design_rules.py`:
`test_the_landing_is_shown_at_rest` — без reveal-on-scroll, без count-up, keyframes только
процессные) этим планом разворачивается — только для лендинга, приложение не трогаем. Дух
правила остаётся: движение показывает процесс (скелет рисуется, цифра измеряется), а не
украшает. Это решение Артура, тест переписывается осознанно.

**Что остаётся как есть (закреплено тестами и данными):**
- H1 «Faster and pain-free / starts with one change», без «Film again» в hero.
- Порядок: результат → отчёт → до/после → Кона; «speed before pain»; источник на каждой
  карточке; никаких обещаний «no more pain».
- CTA ведут в `/app`, не в `/app#signup`. Кнопки `?goal=` в hero — данные для PostHog.
- Пункты главного меню = `.gnav` на публичных страницах (`test_public_nav.py`).
- Meta pixel только на публичных страницах, баннер согласия по региону.
- Pricing рендерится общим `pricing.py`, не руками.

**Риск конверсии.** Пинованные секции и скролл-сцены удлиняют путь до CTA. Apple решает это
кнопкой «Buy» в якорной полосе — делаем так же: «Analyze free» всегда в полосе глав, и у
каждой главы тихая CTA в хвосте. Scroll-jacking (перехват колеса) не делаем вообще: только
нативный скролл, пин через `position: sticky`.

**Производительность.** Страница Apple — 880 KB HTML и сотни кадров. Бюджет для нас: HTML
≤ 150 KB, медиа над сгибом ≤ 1.5 MB, всё лениво ниже; LCP < 2.5 s на телефоне (сейчас
постер 76 KB + клип 2 MB с `preload=metadata` — сохранить). Firefox не умеет
`animation-timeline` — обязателен запасной путь на IntersectionObserver;
`prefers-reduced-motion` — всё в конечном состоянии.

## 3. Техника

**Три примитива, и больше ничего** (всё в одном self-contained `landing.html`, без библиотек):

1. `.pin` — sticky-визуал + шаги текста (Apple scroll-group). `position: sticky` +
   IntersectionObserver переключает `data-step`. Работает везде.
2. `.scrub` — последовательность, привязанная к скроллу: CSS `animation-timeline: view()`
   (Chrome/Edge/Safari), fallback — IO проигрывает один раз при входе. Применение: скелет
   в hero (stroke-dashoffset на SVG-линиях + opacity подписей), шторка до/после, точки Коны.
3. `.count` — цифра считается при входе главы. Только ключевые цифры и дельты.

**Скелет в hero.** Экспортировать per-frame landmarks одного клипа (33×2×N, JSON ≈ 50–100 KB
на 10 s при 30 fps, можно проредить до 15 fps) и рисовать SVG поверх сырого видео/постера
в цветах бренда. Нужен клип **без** вжатого оверлея. Байты меньше, чем у любой WebP-ленты,
и кадр остаётся резким.

**Мобильный свайп.** `scroll-snap-type: x mandatory` для highlights, кинограммы и шагов
«как работает». Вертикальный скролл не перехватывается.

**Якорная полоса глав.** Второй элемент под `.nav`, не трогает `.nav-links`
(`test_public_nav.py` сравнивает именно их).

**Медиа.** Правила из прошлых итераций остаются: постер у каждого видео, `preload=metadata`,
относительные пути `media/…`, одна версия файла в `?v=`.

**Тесты.**
- `test_design_rules.py`: лендинговые проверки переписать под белый список примитивов
  (`pin`/`scrub`/`count`) и список keyframes; правила приложения не трогать.
- `test_landing_order.py`: новые баннеры секций, те же инварианты (результат раньше отчёта,
  proof сразу после отчёта, Кона после proof, источники, нет обещаний боли, якоря существуют);
  правило чередования фонов заменить на правило темы глав (dark 1–8 / light 9+).
- Playwright: без горизонтального скролла на 390 px, LCP-бюджет, оба пути (с
  `animation-timeline` и без — Firefox), `prefers-reduced-motion`.

**Аналитика.** Новые события PostHog: `landing_chapter_view` (id главы, макс. глубина) и
